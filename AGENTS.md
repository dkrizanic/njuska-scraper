# Engineering Guidelines for AI Agents & Contributors

This repository enforces strict engineering standards for all AI coding agents, contributors, and automated tooling.

---

## 1. Git Commit Rules

AI agents must strictly adhere to the Conventional Commits specification:

```
<type>(<scope>): <imperative summary>

[optional body explaining motivation and architectural impact]
```

### Allowed Types
- `feat`: A new user-facing feature or API capability
- `fix`: A bug fix in scraping, API, or frontend
- `refactor`: Code restructuring without changing functionality (e.g. MVC migration)
- `perf`: Performance improvement (e.g. DB indexing, connection pooling, batch inserts)
- `test`: Adding or updating tests
- `chore`: Dependency updates, tooling, configuration
- `docs`: Documentation updates

### Scopes
- `server`, `client`, `scraper`, `api`, `cron`, `db`, `ui`

### Absolute Commit Rules
1. **No AI Signatures**: Never mention "AI", "LLM", "Generated by Assistant", "Cursor", "Copilot", or prompt details in commit titles, descriptions, or git tags. All commits must reflect professional senior engineer work.
2. **Imperative, Lowercase Subject**: Write `feat(api): add pagination support`, NOT `feat(api): Added pagination` or `feat(api): adds pagination.`.
3. **Character Limit**: Keep the subject line under 72 characters.
4. **Focused Diffs**: Do not combine unrelated refactors with functional changes in a single commit.

---

## 2. Prohibition on AI Comments ("No AI Comments Policy")

AI agents must **never** add robotic, low-value commentary to code:

### Forbidden Patterns:
- ❌ Comments stating what the next line obviously does:
  ```ts
  // Fetch listings from database
  const listings = await getListings();
  ```
- ❌ Robotic or conversational meta-comments:
  ```ts
  // Here we check if user is admin
  // Auto-generated helper
  // Created by AI assistant
  ```
- ❌ Verbose docstrings that simply repeat function names and parameter types already captured by TypeScript.

### Permitted Comments:
- Explaining non-obvious business/domain logic (e.g., specific Zagreb real estate tax quirks or sublease margin formulas).
- Workarounds for upstream library bugs or specific third-party anti-bot heuristics.
- Complex regex explanations.

Code must be self-documenting through explicit naming, single-responsibility functions, and strict TypeScript types.

## 3. Rules for Writing AI Tests

When asked to write or maintain tests, AI agents must focus on high-impact, lean test suites rather than vanity code coverage:

### What to Test:
1. **API Integration Contracts**:
   - HTTP status codes (200, 400, 404, 500).
   - Expected response envelope schemas (e.g. `{ total, items, page, limit }`).
   - Query filter propagation (e.g., verifying `category=rent` filters out sale listings).
2. **Critical Business Calculations**:
   - Pure algorithmic functions (e.g. rent-to-rent arbitrage discount %, revenue tier calculation).
   - Edge cases: zero living area, negative price, division by zero when neighborhood average is 0.

### What NOT to Test:
- ❌ Do not write tests that only verify that a mock function was called with identical mock arguments.
- ❌ Do not test trivial getters, setters, or pass-through wrappers.
- ❌ Do not generate huge snapshot tests of raw HTML or database rows that break on trivial text changes.

### Test Performance:
- Keep backend integration and unit tests runnable within seconds via `npm test` using native Node.js test runner (`tsx --test`).
- If a test failure does not indicate an actual broken user flow or contract violation, that test should not exist.
